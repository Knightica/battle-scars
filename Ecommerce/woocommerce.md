# WooCommerce

**Use for:** WordPress-based e-commerce stores, Israeli market (ILS, VAT, IL-only selling)
**Status:** Active

## Setup & access

- Configure via WP REST API, not the WC setup wizard UI: faster, scriptable, repeatable.
- **Israel locale defaults:** store base Tel Aviv / IL, currency ILS (symbol Shekel), currency position right with a space after the amount, weight unit kg, dimension unit cm, selling restricted to Israel only.
- **VAT / tax:** prices include 18% VAT. Tax based on store base. Totals itemized at checkout. Create an IL VAT rate (Hebrew label for VAT); on a fresh install it lands as id 1.
- Set store admin email explicitly via REST after install: WC defaults to the WP admin email which may be wrong.
- Hide WC onboarding nags after setup: `POST /wc-admin/onboarding/tasks/setup/hide` and `/extended/hide`. Bulk-action all inbox marketing notes to keep admin home clean.
- Credentials (WP Application Password + host API key) go in `.env` (gitignored). Keep a master copy in a password manager. Never commit.

## Scars & gotchas

- **Polylang beats TranslatePress for bilingual WC** - Polylang handles cross-language inventory linkage (shared stock, linked product variants across languages) correctly. TranslatePress does not. Use Polylang Free; if you author all copy yourself, auto-translate is not needed.
- **Plugin jungle is a performance and maintenance liability** - Target 10 plugins max (managed garden). Every plugin adds auto-update surface, runtime overhead, security exposure, and cognitive tax. Default answer to "should we install this" is NO. Only install if it passes all 4 criteria: genuinely complex to build, actively maintained, no code/automation pattern already covers it, and cost is clearly lower than building it.
- **ACF Pro is not worth it when you generate the blocks in code** - ACF's value is the visual field builder for human devs clicking through admin. When code generates vanilla WP blocks (block.json + render.php + edit.js + style.css), ACF adds only overhead. Template off a base block pattern instead.
- **Prefer GTM over heavyweight tracking plugins (e.g. PixelYourSite)** - A GTM container gives full control: GA4 base tag, GA4 ecommerce events (view_item, add_to_cart, begin_checkout, purchase), Meta Pixel base + standard events. Bridge WC -> GTM dataLayer via GTM4WP plugin or custom theme code.
- **Meta CAPI must be server-side** - iOS attribution is broken without server-side Conversions API. Route via your server or a proxy. Do not rely on browser-side Pixel alone for purchase events.
- **Prefer a code backend over email-marketing plugins** - Plugin email tools add vendor lock-in and plugin overhead. Newsletter capture and order notifications can go through webhooks writing to a database (e.g. Supabase), then trigger email flows from there.
- **GA4 revenue mapping must be documented per store** - GA4 revenue figures do not automatically match WooCommerce order totals. Decide and document whether GA4 purchase value maps to WC subtotal, subtotal + shipping, or net (pre-VAT). This is a recurring gap when comparing GA4 vs WC dashboards. Cross-reference ga4.md.
- **Live WC store gets its own server** - Noisy-neighbor risk during checkout is an avoidable failure mode. Pre-launch / staging / brochure sites can share. A live e-commerce store with real transactions should be isolated on its own server.
- **Git Deploy over rsync-over-SSH on managed hosts** - Some managed hosts (e.g. Cloudways) disable shell access for app users via ForceCommand even with valid keys. A host-native Git Deploy feature (wired via a deploy key on the GitHub repo) bypasses this entirely. On GitHub, set `deploy_keys_enabled_for_repositories` to true at the org level.
- **Israeli accessibility law (Takana 35 / IS 5568 / WCAG 2.0 AA) applies to WC stores** - Do not install an accessibility widget (the popup with the wheelchair icon). Build accessibility into the code: semantic HTML, keyboard navigation, 4.5:1 contrast, ARIA labels, skip-to-content link, no autoplaying media with sound. Publish a Hebrew accessibility statement page (required, dated, named coordinator).
- **A hardened WC site's WAF blocks custom REST + admin-ajax, but allowlists `wc/v3` - register your custom reader under `wc/v3`** - On a Cloudflare-fronted, security-hardened WooCommerce store, every self-serve way to add a JSON endpoint was blocked at the WAF with an HTML "403 Forbidden" block page **before reaching WordPress** (confirmed identical from curl AND a normal browser): (a) a custom REST namespace `/wp-json/custom/v1/*` - blocked on ANY leaf route regardless of name; the namespace *index* returned 200 but executing a route 403'd; (b) a custom `admin-ajax.php` nopriv action (GET) - blocked the moment the action was registered and ran (an unregistered action returned WP's `0`/400 and passed, so the block keys on the custom nopriv handler executing); (c) POST to `admin-ajax.php` - nginx `405 Not Allowed` at the web-server level. What PASSES: core `/wp-json/wp/v2/*`, `/wp-json/wc/v3/*` (incl. **arbitrary nonexistent** subpaths, which return a clean WP `404 rest_no_route`, proving the WAF allowlists the namespace *prefix*, not a route whitelist), and another installed plugin's namespace index. **Fix: `register_rest_route('wc/v3', '/<your-route>', ...)` and authenticate with the existing WooCommerce consumer key/secret (Basic auth).** WC's own REST auth (`WC_REST_Authentication`, which fires for any `/wc/` URI) then populates the admin user, so a `permission_callback` of `current_user_can('manage_woocommerce')` gates it - no separate secret needed (keep a bearer-key fallback in case WC auth doesn't populate the user). Don't burn hours renaming routes/keywords; it's a namespace-prefix allowlist.
- **CartFlows "Cart Abandonment Recovery" captures email-FIRST, so its table is an email pool, not a phone/WhatsApp pool** - The free "Cart Abandonment Recovery for WooCommerce" plugin (Brainstorm Force/CartFlows) writes captured carts to `wp_cartflows_ca_cart_abandonment`. Gotchas: (1) **no REST endpoint** - read it via a `$wpdb` SELECT in a snippet (see the `wc/v3` scar above). (2) `other_fields` and `cart_contents` are **PHP-serialized** (`a:21:{...}`), NOT JSON - `maybe_unserialize()` server-side or parse on the client. (3) **Capture triggers on the email field**, so for shoppers who abandon at/near the email step, `email` is populated but `wcf_first_name`, `wcf_last_name`, and `wcf_phone_number` are **empty** (one real month: 12 abandoned rows, `email` on all, phone on **0**). So for **WhatsApp** recovery this table is useless - the only phone-bearing abandoners are the ones who completed checkout to the payment step, i.e. native WC `pending`/`cancelled-unpaid` orders (which carry full `billing.phone/email/first_name`). To turn the CartFlows pool into a WhatsApp pool, **reorder checkout so phone sits above email** (Checkout Field Editor plugin) so phone is filled before the capture fires.
- **Unpaid checkouts can age `pending` -> `cancelled` on a ~weekly sweep** - A gateway (seen with Gobit/Tranzila) leaves unpaid attempts as `pending`; a batch job flips them to `cancelled` about weekly (visible as `date_modified` clustered on sweep dates). So `pending` + recently-`cancelled`-unpaid are the SAME abandoned-cart population at different ages, and a recovery automation must fire FAST (hours, while still `pending`) before the sweep buries them. Check the store's own aging behavior (`failed`/`checkout-draft` may stay at 0) before designing the recovery window.

## Conclusions / best practices

- Configure WC via REST from day one: it is reproducible, auditable, and avoids clicking through the setup wizard on every new store.
- Lock your plugin list before starting. Every plugin added mid-build is harder to remove. Audit against the 4-criteria test before installing anything new.
- Polylang is one of the few plugins that genuinely earns its slot for bilingual WC stores in Israel. Keep it.
- Tracking architecture: GTM as the single container, GA4 + Meta Pixel inside it, Meta CAPI server-side. Do not mix plugin-based tracking with GTM, pick one.
- Email and automation flows belong in a code backend + database, not WP plugins. Easier to maintain, no plugin update risk, portable across projects.
- Document the GA4-to-WC revenue mapping for each store at setup time, not after someone questions the numbers.
- Hosting: one server per live e-commerce store. Stage / dev can share.
- SEO migration: preserve `/product/[slug]/` URLs across rebuilds. 301-map everything else. Submit new sitemap to GSC immediately post-launch and monitor 404s for 4 weeks.
