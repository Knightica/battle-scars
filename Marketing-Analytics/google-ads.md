# Google Ads

**Use for:** Paid search and display, driven programmatically through the Google Ads API rather than the UI.
**Status:** Active

## Setup & access

- **Two account types, and you need both.** A **manager account** (MCC) runs no campaigns and holds no billing; an **ad account** runs the campaigns. The manager exists for two reasons: Google issues **developer tokens only to manager accounts**, and it is how client accounts are managed without sharing logins.
- **Auth that works:** a domain-wide-delegation service account impersonating a user who has access to the accounts. Add the scope `https://www.googleapis.com/auth/adwords` to the DWD client, keep every existing scope, and mint the token the same way as any other Google Workspace API access. No OAuth client, no refresh-token dance, no extra secret beyond the developer token.
- **Headers:** `Authorization: Bearer <token>` + `developer-token: <token>` + optionally `login-customer-id: <manager id, digits only>`.
- **Endpoint:** `https://googleads.googleapis.com/<version>/customers/<cid>/googleAds:search` for GAQL, `.../<resource>:mutate` for writes. Customer ids are digits only, no dashes.
- Keep the developer token in a secret store, read at runtime. Never hardcode it.
- An **official Google Ads MCP** exists but is **strictly read-only** - no bids, no pausing, no asset creation. Writes must go through the API directly.

## Scars & gotchas

- **The Ads API must be enabled on the service account's GCP project, and the error names the project by NUMBER** - The first call returns `403 Google Ads API has not been used in project <project-number> before or it is disabled`. That number is the project id of whatever credential you authenticated with, not the Ads account, and it is easy to misread as an Ads permissions problem. Enable `googleads.googleapis.com` on that project and retry after a minute.

- **`login-customer-id` set to a manager the account is not actually linked under returns `USER_PERMISSION_DENIED`, which reads like an auth failure** - Setting the header to the manager id fails with a flat "The caller does not have permission" for any account not yet linked beneath it, even when the impersonated user has full direct access to that account. Dropping the header (or setting it to the account's own id) succeeds immediately. Diagnostic: if a direct call works and the manager-context call does not, the problem is the account **link**, not permissions.

- **Linking a GA4 property auto-creates the key events as conversion actions, all at status `HIDDEN`** - After linking, the Ads account already contains one conversion action per GA4 key event, named `<stream> (web) <event_name>`. They look absent in the UI's default view and present in the API, and they do nothing at all until set to `ENABLED`. So "we still need to import conversions" is usually wrong; the correct task is to enable the ones you want and leave the rest hidden.

- **A GA4-imported conversion action binds to PROPERTY + EVENT NAME, not to a data stream, and its auto-generated name lies about that** - The action is created as `<property display name> (web) <event_name>`, e.g. `example.com (web) schedule`, which reads like it only counts conversions from that domain. It does not: `googleAnalytics4Settings` holds only `propertyId` and `eventName`. On a property with two data streams (two sites), **one conversion action counts the event from both**. So a multi-site setup needs no second conversion action, and changing a campaign's landing page to the other site does not require reconfiguring conversions. The campaign wizard will still re-prompt "set up how you want to measure this goal" when you change the destination URL; pick the same event again.

- **Every enabled conversion category defaults to `biddable: true` - enabling three conversions silently makes all three primary** - There is no prompt and no warning. Enable a booked-appointment, a lead-form and a newsletter conversion and the account will bid for all three equally, so the algorithm chases whichever is cheapest, which is usually the newsletter signup. You must explicitly `biddable: false` every category except the one you actually want optimised.

- **`biddable: false` is OMITTED from the API response, not returned as `false`** - Protobuf JSON drops default values, so a secondary goal comes back with no `biddable` key at all. Reading the response literally makes it look like the field failed to write. Absent means false.

- **`conversion_action.primary_for_goal` no longer exists (removed by v21)** - Selecting it returns a bare `INVALID_ARGUMENT` that does not name the offending field, which sends you hunting through the whole query. Primary vs secondary now lives on **`customer_conversion_goal`** (account default, inherited by every campaign) and **`campaign_conversion_goal`** (per-campaign override), via the `biddable` flag on a **category**, not on an individual conversion action.

- **Bidding optimises on the conversion CATEGORY, and GA4-imported events land in useless categories** - A GA4 key event imported as a conversion action arrives with category `DEFAULT`, the catch-all. Since goals are set per category, leaving it there means the thing you care about cannot be made primary in any meaningful way. Recategorise on import: booked calls -> `BOOK_APPOINTMENT`, contact forms -> `SUBMIT_LEAD_FORM`, newsletters -> `SIGNUP`.

- **`customerConversionGoal` resource names are `{CATEGORY}~{ORIGIN}`** - e.g. `customers/<cid>/customerConversionGoals/BOOK_APPOINTMENT~WEBSITE`. Undocumented in the obvious place and unguessable if you expect a numeric id. `ORIGIN` is `WEBSITE` for anything coming from a GA4 web stream.

- **"Explorer access" is a real working tier, not a dead one - it reads AND writes, but blocks account management** - A freshly issued developer token sits at **Explorer access**. Unlike the old "test account access" it is genuinely useful: GAQL queries against production accounts work, and so do `conversionActions:mutate` and `customerConversionGoals:mutate`. What it refuses is account-management methods such as `customerClientLinks:mutate` (linking an account under a manager), with `DEVELOPER_TOKEN_NOT_APPROVED` and the message *"This method is not allowed for use with explorer access. Please apply for basic or standard access."* So do not conclude from a successful read that the token is approved; the gap only shows up on the specific method you need. Apply for **Basic** in API Center.

- **Explorer access capability map (measured, not documented)** - Tested on a live account. **Allowed:** all GAQL reporting, `conversionActions:mutate`, `customerConversionGoals:mutate`, `sharedSets:mutate` and `sharedCriteria:mutate` (so shared negative keyword lists can be built in full). **Blocked:** `customerClientLinks:mutate` (linking an account under a manager) and `generateKeywordIdeas` (Keyword Planner). The pattern is that account-management and planning services need Basic; day-to-day configuration does not. Note the **UI Keyword Planner still works** while the API method is blocked, so keyword research is never actually gated on approval.

- **The error `details` array can hold several errors, and the first one can be a red herring** - The same failing call surfaced `UNSUPPORTED_VERSION` ("Version v21 is deprecated") and `DEVELOPER_TOKEN_NOT_APPROVED` in different detail blocks. Printing `details[0]` alone sent the diagnosis down the wrong path entirely. Always iterate every entry in `error.details[*].errors[*]` before concluding anything.

- **Old API versions 404 rather than returning a version error** - Versions several majors behind return a generic Google 404 HTML page, which looks like a wrong URL rather than a sunset version. The newest version answers normally, the one or two behind it still answer with a deprecation warning on some calls, and the version before that already rejects with `INVALID_ARGUMENT`. Probe downward from the newest version when unsure; an HTTP 404 with an HTML body means the version is gone, a JSON error body means the version is alive and something else is wrong. Pin the newest and re-probe periodically - the ceiling moves every few months.

- **Mutate responses return only `resourceName`, never the new state** - A successful `:mutate` proves the call was accepted, not that the field holds what you intended. Always follow a write with a read query. A conversion-goal write can return clean resource names while a field still needs a second pass to actually land.

- **The new-account wizard forces campaign creation, and the escape is two steps** - A new Ads account drops you into an express flow that will not let you finish setup without building a Smart campaign, which also creates Google's own guessed conversion tracking instead of your GA4 conversions. Escape: **"Switch to Expert Mode"** (small link at the very bottom of the page), then **"Create an account without a campaign"** (lower-left of the next screen). The skip option does not appear until after the Expert Mode switch, which is why it seems absent. Switching to Expert Mode is one-way.

- **An unfinished account can vanish and leave a dangling GA4 link** - An Ads account created but never completed disappeared from the account switcher while its GA4 -> Ads link survived, so the property listed two linked customers and only one was reachable. Check `properties/<id>/googleAdsLinks` against the accounts you can actually open, and delete links pointing at accounts nobody can reach.

- **Google silently auto-creates a `WEBPAGE` conversion action and makes it the primary one, sidelining every GA4 import** - An action named `Submit lead form`, type `WEBPAGE`, appears without anyone creating it (Ads infers it by scanning the site) and lands `primary_for_goal=true`. Every properly imported GA4 action then sits at `primary_for_goal=false` **and** `include_in_conversions_metric=false`, so they do not even reach the Conversions column. Bidding optimises toward Google's page heuristic while the instrumented event is invisible. The campaign builder shows only a warning triangle next to "1 action". Audit `conversion_action.type` after any GA4 link: if a `WEBPAGE` action is primary, demote it.

- **`include_in_conversions_metric` is immutable and follows `primary_for_goal`** - Sending both fields in one update returns `IMMUTABLE_FIELD` for the whole operation, which reads as if the action cannot be edited at all. Only mutate `primary_for_goal`; the include flag flips to match on its own. Verified by mutating each field alone with `validateOnly=true`: `primaryForGoal` MUTABLE, `includeInConversionsMetric` IMMUTABLE.

- **API versions get hard-blocked, not just deprecated, and the ceiling moves every few months** - An old version can flip from "deprecated warning" to `UNSUPPORTED_VERSION` ("Requests to this version will be blocked") between one check and the next, while several newer versions all work and the very newest hasn't shipped yet. Pinning a version in a helper script is correct, but re-probe the ceiling before assuming an old script still runs: the failure surfaces as a generic `400 INVALID_ARGUMENT`.

- **Basic Access approval does not change anything you can see in the account** - The approval email arrives for the developer token on the manager account, and the token string is unchanged. Nothing needs re-storing or re-issuing; the only difference is the daily operation cap (15,000/day vs the test-account-only restriction). Verify by calling `listAccessibleCustomers` against a real account rather than trusting the email.

- **Keyword Planner matches Hebrew `AI` onto `AIG` and floods the results with insurance searches** - Seeding `generateKeywordIdeas` with a Hebrew term for "AI agent" for geo Israel returned a result set dominated by AIG insurance terms (travel insurance, car insurance, and a dozen more), several with higher volume than any real idea. Filter them out of the plan **and** add the relevant insurance-brand terms as campaign negatives before launch, or a meaningful share of the budget goes to people shopping for car insurance.

- **Hebrew's language constant is code `iw`, id `1027`, not `he`** - Querying `language_constant WHERE code = 'he'` returns nothing and reads like the language is unsupported. Google uses the deprecated ISO code `iw`. Safer lookup is by name: `WHERE language_constant.name = 'Hebrew'`.

- **Switching a campaign to a parameterless bidding scheme rejects the obvious field mask with `FIELD_HAS_SUBFIELDS`** - `update: {maximizeConversions: {}}` with `updateMask: "maximize_conversions"` fails because the mask names a message field. The working form masks a subfield and writes its default: `maximizeConversions: {targetCpaMicros: "0"}` with `updateMask: "maximize_conversions.target_cpa_micros"`. Same pattern applies to any oneof bidding scheme switch.

- **Google's ad-review crawler shows up in GA4 as real paid traffic, and it hits the account's business website, not the campaign's final URL** - After linking Ads to GA4, a stream showed dozens of `google / cpc` sessions with campaign `(not set)`, landing page `/`, 0 seconds, Chrome desktop, country `(not set)`, and exactly `first_visit` + `page_view` + `session_start` each. They clustered on the days the account was edited and landed on the account's default business site even though every actual ad pointed somewhere else. It was misread for weeks as one site's tracking leaking into the other's GA4 container. Fingerprint: campaign `(not set)` + country `(not set)` + 0s + one session per cookie. Ignore it, or filter paid reports by campaign name; there is nothing to fix on the site.

- **Applying one recommendation card in the UI can apply neighbours you did not pick, and one of them re-adds broad match** - An operator applied the callout and structured-snippet recommendations from the Recommendations page. `change_event` showed that in the same session, `client_type = GOOGLE_ADS_RECOMMENDATIONS` also CREATEd a BROAD duplicate of every phrase-match keyword ("Add broad match keywords"), silently undoing an earlier broad-to-phrase cleanup. Nothing in the UI flagged it. After any UI session on the Recommendations page, query `change_event WHERE change_event.client_type = 'GOOGLE_ADS_RECOMMENDATIONS'` and read the `new_resource` of every AD_GROUP_CRITERION create. Also check `recommendation_subscription` for auto-apply (a click is different from a standing subscription, and the log tells you which happened).

- **Maximize Conversions with a near-zero conversion history triples CPC and paces to 2x budget** - Measured on the same keywords, ad and geo, in the account's local currency: Max Clicks with a bid cap ran at roughly 1x the cap in average CPC; Max Conversions with a single conversion of history ran at nearly 3x that CPC, hit twice the cap on single days, spent close to double the daily budget (legal under the monthly cap) and went budget-limited on the large majority of impressions. The strategy has no ceiling and nothing to learn from, so it just buys volume. Do not switch to conversion bidding under roughly 15 conversions in 30 days, and if a client insists, re-check after a week with `metrics.average_cpc` and `search_budget_lost_impression_share` by date.

- **Reverting to Maximize Clicks with a CPC cap: `targetSpend: {cpcBidCeilingMicros}` with mask `target_spend.cpc_bid_ceiling_micros`** - Maximize Clicks is the `TARGET_SPEND` scheme in the API. Same `FIELD_HAS_SUBFIELDS` trap as the other bidding switches: mask a subfield, not the message. Read back `campaign.bidding_strategy_type` (expect `TARGET_SPEND`) and `campaign.target_spend.cpc_bid_ceiling_micros`.

- **Ad schedules are campaign criteria, one per day, and setting any at all turns off every other hour** - `campaignCriteria:mutate` create with `adSchedule: {dayOfWeek, startHour, startMinute: 'ZERO', endHour, endMinute: 'ZERO'}`; hours are in the account time zone (`customer.time_zone`). A day with no criterion gets no ads at all, so "skip this weekday" is expressed by simply not creating a criterion for it. Read back with `campaign_criterion.type = 'AD_SCHEDULE'`. One campaign found close to half its spend landing on the weekend with zero conversions, plus paid clicks in the middle of the night, before a schedule was ever set.

- **`search_term_view` only shows terms above a privacy threshold; sum its `cost_micros` against the campaign's to see how much spend you cannot audit** - On one campaign the visible terms covered roughly a third of total spend. The remainder is "other search terms", and negatives can only be written for what you can see. A low visible share is itself a reason to tighten match types and pause low-QS keywords rather than keep hunting negatives.

- **`user_location_view` with `targeting_location = false` is where "presence or interest" leakage shows up** - Rows with `targetingLocation: false` are users physically outside the targeted location. Country ids are `2000 + ISO 3166-1 numeric` (2376 Israel, 2275 Palestinian Territories, 2398 Kazakhstan). Fix is `geoTargetTypeSetting.positiveGeoTargetType = 'PRESENCE'`, mask `geo_target_type_setting.positive_geo_target_type`.

## Conclusions / best practices

- **Exactly one conversion category should be biddable.** Pick the one closest to revenue (a booked call, not a form fill, and never a newsletter signup), make it primary, and leave everything else measured but secondary.
- **Set goals at account level, override per campaign only when there's a real reason.** The account default is inherited by every campaign, so getting it right once removes a step you would otherwise have to remember forever.
- **Recategorise every imported GA4 conversion.** The imported category is a guess and it is what bidding actually uses.
- **Assign conversion values.** Without them Ads optimises for count and treats every conversion as equal. Rough is fine: average deal value x close rate.
- **Never manually UTM-tag Ads links** when auto-tagging is on; it double-tags. See `utm-policy.md`.
- **Read after every write.** Mutate responses are receipts, not state.
- **Guardrail for agent-driven accounts:** structural changes (conversion actions, negative keywords, ad copy, audiences, campaigns created **paused**) can be automated freely; anything that increases spend (enabling a campaign, raising a budget or bid, changing bid strategy) gets a human confirmation. Unlike analytics work, a bad write here costs cash.
