# ManyChat

**Use for:** WhatsApp messaging via ManyChat - confirmation flows, webinar reminders, broadcast campaigns, funnel welcomes.
**Status:** Active

## Setup & access
- API token: `MANYCHAT_API_TOKEN`
- Flow IDs: one env var per flow (`MANYCHAT_FLOW_WEBINAR_CONFIRMATION`, `MANYCHAT_FLOW_PAYMENT_WELCOME`, etc.)
- Custom field IDs: stored as env vars (`MANYCHAT_FIELD_WEBINAR_DATE`, `MANYCHAT_FIELD_PHONE_LOOKUP`, `MANYCHAT_FIELD_ATTENDANCE_ID`, etc.)
- Subscriber lookup: `findBySystemField` cannot match `whatsapp_phone` (API limitation). Seed a custom text field `phone_lookup` on every subscriber create and use `findByCustomField` for all lookups.
- Rate limit: 1 req/sec. Enforce via a chained-promise pacer plus a shared `manychat-api` queue (concurrencyLimit:1).
- Wallet must be topped up. Zero balance causes `sendFlow` to fail with an opaque "Validation error".
- WhatsApp Template must be the first MESSAGE/ACTION node in a flow when sending outside the 24h session window - any message or action node before it causes "Validation error". Logic nodes are fine: Condition splits BEFORE the template work (verified live: trigger -> two Condition nodes -> template sent OK to a cold-window subscriber).

## Scars & gotchas
- **Meta 3050: marketing templates blocked to US numbers** - `sendFlow` fails with `{"code":3050,"message":"Meta disabled the use of marketing templates on US numbers, try a utility template instead"}` when the flow's first message is a Marketing-category WhatsApp template and the subscriber has a +1 number. Onboarding/welcome confirmations legitimately qualify as Utility - duplicate the template as Utility and point the flow at it. Until then, US-number members silently miss the flow (email fallback still works).
- **sendFlow "accepted" is not "delivered"** - a successful sendFlow response only means ManyChat queued it; Meta can still drop delivery downstream (e.g. per-user marketing-template caps). Delivery status is visible only in the ManyChat UI chat thread, not via API. Subscribers with `last_interaction: null` (never sent an inbound message) are reachable ONLY via template messages - free-form flow steps to them silently no-op.
- **High-volume marketing-template blast drops some deliveries; a single direct resend recovers them** - a few-hundred-recipient template-first flow blast counted everyone as `sent` (200), but at least one converter (`last_interaction: null`) never received it, until an isolated `sendFlow` resend to the same subscriber ~3h later landed immediately. Two lessons: (1) the flow WAS template-first (it reached a `last_interaction: null` cold opt-in on the lone resend), so `last_interaction: null` is NOT a reliable non-delivery predictor for a template-led flow - the blast-time miss was a downstream Meta drop under volume, not a template/window problem. (2) Delivery is not API-observable, so you cannot script a "who missed it" audit from `getInfo`; only the ManyChat UI chat thread / flow delivery stats show truth. If a blast recipient reports non-receipt, a direct one-off resend is the cheap fix.
- **"Pause automations" on a subscriber silently swallows sendFlow** - a subscriber with the ManyChat "pause automations" toggle on (or `optin_phone: false` with no open 24h window) returns `200 {"status":"success"}` from `POST /fb/sending/sendFlow` but the message is never delivered. There is NO signal in the API response, and a task that calls sendFlow will count them in its `sent` tally, not `failed` - so run summaries over-report delivery. When diagnosing a "didn't receive it" complaint, check the subscriber's `optin_phone` and pause state via `getInfo` (and ultimately the UI chat thread) before trusting a green run. A real case: a registrant was correctly resolved and sent (200) but paused, so never got the reminder while showing up as delivered.
- **sendFlow "Validation error: Automation does not exist" = the flow is unpublished** - `POST /fb/sending/sendFlow` returns `{"status":"error","message":"Validation error","details":{"messages":[{"message":"Automation does not exist"}]}}` when the flow namespace (`content2026..._xxxxx`) points at a DRAFT flow. The ns appears in the ManyChat CMS URL the moment you create the flow, but sendFlow only accepts it once the flow is **published** - and publishing mints a DIFFERENT ns (draft `content<ts>_<draft-id>` becomes published `content<ts>_<published-id>`). So grab the id from the URL AFTER publishing, not from the draft. Symptom: a freshly-wired welcome/CTA flow hard-fails every send until published.
- **setCustomFields is all-or-nothing** - one invalid field value in the batch 400s the ENTIRE call (`{"message":"Validation error","details":{"messages":[{"message":"Field[N] with invalid value"}]}}` where N is the 0-based index), so none of the fields get set. Notably an **empty string** is rejected by some field types - passing `field_value: ""` for a location/text field fails validation. Always send non-empty valid values (fetch the real data first); if a value is genuinely unknown, omit that field from the batch rather than sending `""`.
- **Blast queue starvation** - a ~700-recipient blast on the shared `manychat-api` queue (concurrencyLimit:1) blocked a live event's hour-before reminder for ~40 min. Real throughput was ~3.5s per blast child (3-4 API calls through the 1 req/sec pacer), not the estimated 1s. Mitigate by deploying a no-op child to drain the queue before webinar start. Fix: dedicated `manychat-blast` queue with its own concurrency + a separate global pacer; OR gate blasts on "no webinar starting within 2h" before fanning out.
- **Ad burst starving funnel welcomes** - ad-platform bursts can stack dozens of `direct-funnel-signup` tasks behind each other on the shared `manychat-api` queue, delaying welcome messages. Fix: dedicated `manychat-direct` queue (concurrencyLimit:1) isolated from all other queues.
- **Duplicate wa_id on organic WhatsApp contacts** - `createSubscriber` fails with a duplicate `wa_id` error when the contact was added to ManyChat organically outside your funnel. Fix: catch the error, look up the subscriber by name, trust the result only if the WhatsApp number matches, then seed `phone_lookup` on both the create path and the recovery path. Self-heals on next run.
- **Email-fallback dedup collision on double tickets** - two seats under one purchase share the buyer's email; a lookup resolves both seats to the same contact, linking two attendees to one CRM row. Fix: track `claimedContactIds` per purchase; when a lookup returns an already-claimed contact, create a separate contact carrying only genuinely-own fields (a phone/email that was actually submitted for another seat belongs to the buyer and is dropped).
- **Custom fields must be set before sendFlow** - `setCustomFields` must be called before `sendFlow` or template vars like `{{webinar_date}}` render empty. dozens of blast messages once went out with blank dates because webinar_date/time fields were missing from the first payload batch.
- **"Validation error: Automation must be published" / generic "Validation error"** - returned for non-engaged subscribers or un-published automations. These are expected and should be soft-skipped, not retried.
- **Stale `{{first_name}}` on pre-existing subscribers** - if a subscriber already exists in ManyChat under a different name, the flow renders the old name. Fix: call `updateSubscriberName` before sending any welcome flow to a pre-existing subscriber.
- **Silent ManyChat confirmation failures** - a background task run can complete green while the buyer never receives their WhatsApp message. Fix: fire a Telegram alert to an Alerts group when a confirmation send returns `sent:false` or throws a hard error, so misses surface immediately.
- **1 req/sec rate limit** - a shared `manychat-api` queue (concurrencyLimit:1) plus a `pace()` interceptor enforces the 1 req/sec hard limit. The pacer pattern is non-negotiable.
- **Hebrew (i18n) first name requirement** - if your templates interpolate a localized (e.g. Hebrew) first name, subscribers must always have that field set. Pre-approved WhatsApp templates interpolate it; missing = render gap or Meta rejects the send. Derive it: if the lead has a native-script name use the first word, else reverse-transliterate from Latin. Never overwrite a non-empty value. Enforce it centrally at the single upsert point; any future helper that creates or touches a subscriber must also enforce it.
- **The phone-lookup custom field must be populated on all subscribers for dedup** - the env var holding the custom-field ID (`MANYCHAT_FIELD_PHONE_LOOKUP`) is used to find subscribers by phone. Every subscriber create must seed this field; missing values break all downstream phone-based lookups and dedup.
- **ManyChat `findSubscriberByPhone` can hang with no per-call timeout** - the ManyChat backend hangs on `findSubscriberByPhone` calls when no HTTP-client timeout is set. In one incident the task hit MAX_DURATION_EXCEEDED after 5 min with zero CRM writes and no partial progress. Fix: enforce a 15s HTTP timeout on every ManyChat client call.
- **ManyChat failures must never block a lead from landing in CRM** - only hard failures (schema validation, the CRM `create_item`) should throw. ManyChat failures, audit-note failures, and transliteration fallbacks are all non-fatal and must not prevent a lead record from being written.
- **Number custom fields reject string values** - `setCustomFields` on a NUMBER-type custom field with a string `field_value` (e.g. `"1"`) returns `400 "Value for number custom field should be integer or float"`. Send the raw integer (`1`); text fields still take strings. Bit a nurture-drip router field that was a number type.
- **Adopt Instagram subscribers by `subscriber_id`, not phone** - IG-DM subscribers usually have no phone stored in ManyChat, so phone-based find/create spawns a duplicate WhatsApp subscriber. When the inbound channel already hands you the subscriber id (Instagram, an existing flow's `{{user id}}`), adopt it directly (`getInfo` then heal `phone_lookup` + localized-first-name) instead of resolving by phone. Give your upsert helper an optional `knownSubscriberId` for this.
- **There is NO API path to resolve a WhatsApp subscriber by phone if `phone_lookup` is empty** - a subscriber auto-created when someone WhatsApps the business has NO `phone_lookup` custom field and an empty native `phone` field. `findByCustomField(phone_lookup)` misses (field empty), `findBySystemField` accepts only `phone`/`email` (NOT `whatsapp_phone`, which 400s with "Only phone or email can be specified") and the native `phone` is empty, `findByName` needs the right name, and `createSubscriber` returns `"This WhatsApp ID already exists"` with **no id in the error**. Net: the subscriber exists but is permanently unresolvable, so a later CRM lead can't be linked and no automation can reach them. **Only fix: stamp `phone_lookup` = digits-only phone on EVERY subscriber at conversation-start** via a webhook the Default Reply calls. One-time backfill or self-heal on next message for existing subs.
- **`phone_lookup` value must be digits-only (no `+`, no leading 0)** - the search value is `normalizePhone(phone).replace(/\D/g,"")` (e.g. `972XXXXXXXXX`). ManyChat's `{{wa_id}}` is already this format; `{{whatsapp_phone}}` is `+972...`. A native "Set Field" in the ManyChat UI would store the `+` form and silently never match - stamp it via a webhook that normalizes, not a UI Set-Field action.
- **Send a flow on demand:** `POST /fb/sending/sendFlow {subscriber_id, flow_ns}`. Useful to replay a nurture/welcome flow to a test subscriber.
- **Phone lookups are flaky under load - retry before trusting a miss** - `findByCustomField` / `findBySystemField` intermittently return empty for subscribers that exist: two back-to-back sweeps over the same 60 phones resolved different subsets (51 vs 58). Not a 429 - a clean `{"status":"success","data":[]}`. For any bulk resolve, retry each miss with backoff and only accept "not found" after 2+ clean empty responses; cache resolved ids so reruns don't re-hammer the API.
- **A WA subscriber can exist yet be unreachable via API entirely** - `createSubscriber` 400s with `wa_id already exists`, but findByCustomField and findBySystemField (phone AND email) all miss, and the CRM record carries no stored subscriber id. There is no find-by-wa_id endpoint, so such subscribers are dashboard-only: search the Audience by number in the ManyChat UI and fire the flow manually. Seen on 2 of 60 real contacts in one day-of blast.
- **New accounts have API contact import DISABLED - createSubscriber hard-fails until support enables it** - on a fresh ManyChat account, `POST /fb/subscriber/createSubscriber` with `whatsapp_phone` OR `phone` returns `400 Validation error` with `"Permission denied to import wa_id (/phone). Please contact support to enable this feature"`. This is an account-level anti-spam gate, not a payload problem: no API workaround exists (subscribers can otherwise only enter via inbound message or opt-in widget), so any automation that creates subscribers for people who never messaged the business (cart recovery, order notifications) is hard-blocked. Fix: ask ManyChat support to enable API contact import, framed as low-volume transactional sends to checkout opt-ins (no lists, no bulk). Older accounts often have it enabled, so a reference implementation that works there fails on a new account. TRAP: a createSubscriber that SUCCEEDS for a number that already has a WhatsApp thread with the business is NOT proof the gate is open - warm numbers pass while cold numbers still 400 (a go-live test on the operator's own warm number worked, then every cold production target failed). Verify the gate with a number that has never messaged the account, or wait for support's written confirmation. Also: log per-target error rows only for target-level failures - an account-level gate failure logged per-target permanently blocks those targets from retry. Also note: `phone` creation additionally requires `has_opt_in_sms: true` once phone is non-empty.
- **The import gate covers EVERY identifier, email included, and the error enumerates what is denied** - sending the full createSubscriber payload (`whatsapp_phone` + `email` + `consent_phrase` + opt-in flags) on a gated account returns the warning `"Permission denied to import wa_id, email"` plus `"you must fill in at least one field: Phone or Email or WaId"`: ManyChat strips all identifiers you lack import permission for, and the request then fails as identifier-less. Consequences: (1) adding email/consent_phrase does NOT bypass the wa_id gate; (2) the denied-fields list in the warning is a cheap probe for exactly which import permissions an account has; (3) deleting an existing contact in the dashboard does not open the gate for that number.
- **The import gate DOES open on request - budget ~2 days and expect only wa_id** - ManyChat support enabled API contact import about 2 days after the ticket. What worked: showing the exact JSON payload + the exact 400 response, stating the transactional checkout-opt-in use case (no lists, no bulk), and noting the same code runs on older accounts. They enable per CHANNEL: wa_id import was enabled, email import stays blocked unless an Email/SMS channel is connected to the account - createSubscriber then succeeds but silently drops the email with a `warning` field in the 200 response (`"Permission denied to import email"`). Check the `warning` key on successful creates if you expect multi-channel import.
- **WhatsApp template URL buttons percent-encode the appended variable - query strings cannot ride in it** - a dynamic URL button is base + ONE appended variable, and the variable is URL-encoded on append: `?` `=` `&` `/` become `%3F %3D %26 %2F`, so a variable like `12345/?pay_for_order=true&key=wc_order_x` reaches the site garbled and the target page rejects it (e.g. WooCommerce order-pay: "order invalid"). Also: the Button URL field must contain ONLY the fixed base - pasting the full sample URL into it bakes the sample into every send. Fix pattern: keep the variable to a single clean path segment of unreserved chars (digits, letters, `-`, `_`), and install a tiny public redirect route on the target site that expands the token to the real URL (e.g. `/pay/{orderId}-{orderKey}` -> 302 to the order-pay URL).

## Conclusions / best practices
- Never put blasts and time-critical sends (reminders) on the same queue. Use separate queues with separate concurrency limits.
- Always seed `phone_lookup` on subscriber create. Never rely on system field lookup for `whatsapp_phone`.
- Call `setCustomFields` in one batched call before `sendFlow`. Order matters.
- Soft-skip "Validation error" responses. Alert only on hard, non-retryable failures.
- Gate blasts with a pre-flight check: refuse to fan out if a webinar starts within 2h.
- Use `maxAttempts:1` on blast children with 30d idempotency keys so parent re-runs never double-send.
- Track `claimedContactIds` per purchase when a single transaction can produce multiple CRM lookups.
- **Build every outbound flow template-first (outside-24h capable).** Audiences are mostly funnel opt-ins who never send an inbound message (`last_interaction: null`), so a free-form flow reaches almost no one. Put an approved WhatsApp template as the FIRST node so cold subscribers are reachable. Consequence for diagnosis: on a template-first flow, a "didn't receive it" report is NOT a 24h-window/template problem (the window is not a delivery gate) - it's a downstream Meta delivery drop (common under high-volume marketing-template blasts). Fix with a direct one-off `sendFlow` resend to the subscriber_id, which lands immediately. Delivery stays API-invisible (200 = queued); ground truth is the ManyChat chat thread.
- **Recovery path for unresolvable WhatsApp subscribers: your own CRM record.** When every ManyChat find API misses (empty `phone_lookup`, empty native `phone`, create rejects "already exists" with no id), check whether your own CRM already stores the subscriber id - if you write a ManyChat-id column on every subscriber create, the post-payment flow can fall back to that stored id and still send. Truly orphaned subs (no phone_lookup AND no stored id AND no findable name) remain unreachable by API - resolve manually in the ManyChat dashboard and stamp both fields.
